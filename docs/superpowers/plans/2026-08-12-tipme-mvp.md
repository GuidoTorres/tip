# TipMe MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the complete mock-money TipMe flow from creator signup through confirmed tip, push notification, realtime balance, and completed payout.

**Architecture:** One Next.js App Router application uses Supabase for Auth, PostgreSQL, Storage, RLS, and Realtime. Pure TypeScript owns validation and provider contracts; PostgreSQL functions own atomic financial transitions; server routes verify external events and fan out Web Push after commits.

**Tech Stack:** Next.js stable, React, TypeScript, Tailwind CSS v4, Supabase JS/SSR, PostgreSQL, Vitest, Web Push, native PWA APIs, Vercel.

## Global Constraints

- Fans never create accounts and never confirm payments from the browser.
- Store money only as integer minor units plus an ISO currency code.
- Read the platform fee from `PLATFORM_FEE_BPS=300`; never hardcode 3% in domain logic.
- Keep gateway fees nullable until a provider reports an exact fee.
- Derive balances from immutable ledger entries; never store an editable balance.
- Mock financial simulators must return 404 when `NODE_ENV=production`.
- Keep Supabase service role, VAPID private key, and webhook secrets server-only.
- Support Spanish and English through typed dictionaries.
- Preserve the public route `/<username>`.
- Use TDD for domain, webhook, ledger, payout, anonymity, and push behavior. Configuration and presentational UI do not require cosmetic tests.

- `src/lib/security`: environment parsing, signature verification, rate-limit helper.
- `supabase/migrations`: schema, functions, grants, RLS, Storage policies.
- `supabase/seed.sql`: removable Camila demo dataset.
- `tests`: high-value unit and orchestration tests.

- [ ] **Step 1: Define enums, tables, constraints, and indexes**

  Create the eight required domain tables plus `admin_audit_logs`. Enforce integer amounts, supported currencies, unique normalized usernames, unique provider payment/event IDs, one logical notification per related event/type, and immutable ledger identity.

- [ ] **Step 2: Implement atomic financial RPCs**

  `confirm_tip_from_webhook` locks the tip and webhook event, returns unchanged on an already processed event, validates the transition, inserts gross/platform/gateway ledger rows, creates one notification, records timing, and commits as one transaction. Reversal and payout RPCs insert compensating entries and enforce available balance by currency.

- [ ] **Step 3: Enable RLS and narrow grants**

  Authenticated creators may read only their rows and update only allowed profile/subscription fields. Public users execute only `get_public_creator`; direct public reads of private tables are denied. Admin access depends on immutable role data and sensitive writes remain service-role/RPC-only.

- [ ] **Step 4: Add Storage policies**

  Create the `avatars` bucket contract with creator-owned paths, image MIME restrictions, and a 5 MB limit. Public avatar reads are allowed; writes require ownership.

- [ ] **Step 5: Add removable Camila seed data**

- [ ] **Step 6: Document local/remote SQL verification**

## Definition of done

The implementation is done only when automated verification passes and the mock sequence preserves these invariants: server-only confirmation, one ledger effect per provider event, one logical notification fanned out to all valid devices, client balance refreshed from server data, payout never exceeds available balance, payout completion changes ledger once, anonymous identity never appears, and duplicate events change neither money nor notifications.

Physical Web Push remains explicitly pending until the user completes the supplied iPhone/iPad and Android checklist on deployed HTTPS infrastructure.
